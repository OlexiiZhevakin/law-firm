## Architecture

This is a marketing site for a law firm (HARLIB), built on Next.js App Router with **all page content sourced from a headless Strapi CMS**, not hardcoded in components.

### Locale routing
- Locales: `uk` (default) and `en`, handled by `next-intl` middleware in `proxy.ts` matching `/(uk|en)/:path*`.
- `app/page.tsx` (root, no locale) redirects to `/uk`.
- `app/[locale]/page.tsx` validates the `locale` param and renders `app/[locale]/home/page.tsx`.
- **Note:** `i18n.ts` is present but fully commented out/unused. Translation is *not* done via next-intl message catalogs — instead, components take a `locale: 'uk' | 'en'` prop and branch inline (`locale === 'uk' ? '...' : '...'`) or receive already-localized copy from Strapi. Follow this existing pattern rather than introducing `next-intl`'s `useTranslations`/message JSON files.

### Content flow (Strapi)
- `lib/api.ts` exports `fetchStrapi(endpoint, params)`, the single entry point for all CMS reads. It builds the query string, calls `${NEXT_PUBLIC_STRAPI_URL}/api/{endpoint}`, revalidates every 60s, and unwraps Strapi v5's `{ data: ... }` envelope. On any failure it logs and returns `null` — callers must handle a `null`/missing-field response gracefully (components consistently use `data?.field` with fallbacks). **On a non-OK response the thrown `Error` includes `status`/`statusText`/the full request URL** (not just a bare "Failed to fetch data from {endpoint}") — this is what it took to diagnose a real bug where `/about` silently returned no data: turned out to be a `400 ValidationError` ("Invalid key expertiseAreas") because the frontend requested `populate[expertiseAreas]=*` before that field was deployed on the remote Strapi, not a rate-limit/timeout as first suspected. Don't strip this detail back down to a bare message if you touch this function again — it's cheap (no response body read) and was the difference between guessing and knowing.
- `app/[locale]/home/page.tsx` fetches the whole `home-page` content type in one call, using Strapi's bracket `populate` query syntax to deep-populate each section (`headSection`, `aboutSection`, `blockSection`, `partnerSection`, `servicesSection.clusters.items`), then passes each section's slice of data down as a `data` prop to the matching section component.
- `app/[locale]/components/header/Header.tsx` independently fetches its own `header` content type (nav links, button text), and both `home/page.tsx` and `app/[locale]/services/[slug]/page.tsx` independently fetch the `contact` single type via `fetchContactData(locale)` — header/footer/contact are **not** part of the `home-page` payload. This is the established pattern for any content shared across multiple pages: give it its own Strapi single type and its own `fetchStrapi` call, don't bury it inside `home-page`.
- `lib/api.ts` also exports `fetchStrapiBySlug(endpoint, slug, params)` (unwraps a collection-type's filtered array down to one entry or `null` — Strapi always returns an array from a collection endpoint even filtered to one match), `fetchServicePages(locale)` (list of published `service-page` summaries), and `fetchContactData(locale)`.
- When adding a new CMS-driven section: add the populate path to the relevant `fetchStrapi` call, define a typed `data` prop shape on the section component, and default/guard every field since Strapi may return partial data.
- **Every new block and every new page must be wired to Strapi from the start** — the same way `home/page.tsx` and `Header`/`Footer`/`Contacts` do it. Never hardcode page copy (titles, body text, labels) directly in a component `.tsx` file "for now" — define the content type/fields in Strapi first, fetch it with `fetchStrapi`, and pass it down as a typed `data` prop with `?.` guards. The only text allowed to live in code is UI chrome that isn't editorial content (button aria-labels, the `locale === 'uk' ? ... : ...` micro-strings already used for things like "Address"/"Phones" labels, a listing page's own H1) — anything a non-developer might want to edit later belongs in Strapi.

### Page structure
- Sections live under `app/[locale]/home/section/<name>/` (e.g. `head`, `about`, `block`, `partner`, `services`, `contacts`), each a folder with a `.tsx` component and a co-located `.module.scss`.
- Shared UI lives under `app/[locale]/components/` (header, footer, mobile menu, lang switch, cookie banner, scroll-to-top, seo, button, title, nav links, contactModal, quickContact).
- Section entrance animations are done by wrapping a section in the shared `<Reveal>` component (`app/[locale]/components/reveal/Reveal.tsx`).
- `LangSwitch.tsx` builds its `uk`/`en` links from the **current `pathname`** (via `usePathname()`), replacing only the locale segment (`segments[1]`) and keeping everything after it, plus preserving the current URL hash (for in-page anchor links like `#contacts`). It used to hardcode both links to the locale root (`/uk${hash}` / `/en${hash}`) regardless of what page you were on — switching language from `/uk/services/licensing` silently dropped you on the homepage instead of `/en/services/licensing`. Fixed; the segment-replace approach relies on `service-page`'s `slug` being shared/non-localized across `uk`/`en` (confirmed via the live Strapi API, not assumed) — if a future content type ever has locale-specific slugs, a straight segment swap would 404 and you'd need to resolve the target locale's slug via `documentId` first instead.
- `app/[locale]/privacy/page.tsx` has its own `generateMetadata()` (via `generatePageMetadata()`) and renders two separate components: `PrivacyPolicyEn()` (the approved English legal text, untouched) and `PrivacyPolicyUk()` (the real, lawyer-approved Ukrainian text, sourced from `content/legal/privacy-policy-uk.md` and hand-converted to JSX — no CMS, no placeholders anymore). **`PrivacyPolicyUk`'s structure deliberately does NOT mirror `PrivacyPolicyEn`'s** — H1 is "Політика конфіденційності" (not a translation of "Privacy Policy"), and it has 12 sections in a different order (e.g. "Хто відповідає за обробку" is section 2, not section 11) because it's written against Ukrainian law (Закон "Про захист персональних даних" № 2297-VI, cited by article number) rather than GDPR. This divergence is intentional and confirmed by the client — don't "fix" the two versions into matching structures.
- `PrivacyPolicyUk`'s section 10 ("Файли cookie") links to `/uk/cookies-policy` — the source `.md` had `[Налаштування cookies](/nalashtuvannya-cookies)`, a slug that doesn't exist in this app; the link target was remapped to the real route when converting to JSX, same reasoning as `cookies-policy/page.tsx`'s `LEGACY_INTERNAL_LINK_MAP` below.
- **`PrivacyPolicyEn`'s text (section 1.3) still says "we do not maintain a separate cookie policy"** — stale now that `/cookies-policy` exists as its own document (and `PrivacyPolicyUk`'s section 10 explicitly points to it). Flagged, not fixed — whether/how to edit the English text is a legal-content call, not a code one.
- `app/[locale]/cookies-policy/page.tsx` — a **second, separate** static legal page (distinct from Privacy Policy), sourced from `content/legal/cookies-policy-{uk,en}.md`, not Strapi. Same architecture as `privacy/page.tsx` (own `generateMetadata()`, no CMS, locale branches at the top), but the markdown is read via `fs.readFileSync` at request time and rendered through `react-markdown` (+ `remark-gfm` for the GFM table in section 4, + `rehype-raw` so the single embedded `<button data-cookie-settings>` tag in the source markdown survives — react-markdown drops raw HTML by default) instead of hand-written JSX per paragraph. `CookiesPolicy.module.scss` mirrors `/privacy`'s typography (Playfair Display headings, Inter body, 800px max-width) as real classes instead of inline `style={}`.
- The markdown's `<button data-cookie-settings>` (an inline "open settings" CTA authored directly into the legal text) is intercepted by a `components.button` override in `page.tsx` and swapped for `CookieSettingsTrigger.tsx` — a new generic version of `CookieSettingsLink.tsx`'s dispatch-`COOKIE_SETTINGS_EVENT` logic that accepts arbitrary `children` instead of a hardcoded label. `CookieSettingsLink.tsx` (Footer) now wraps this same shared component rather than duplicating the `onClick` handler.
- **The source `.md` files contain internal links to slugs that don't exist in this app** (`/polityka-konfidentsiynosti`, `/privacy-policy` — presumably written against a different site's routing). The markdown text itself is untouched (it's the client's legally-reviewed content, not ours to edit), but `page.tsx`'s `resolveHref()` remaps those two specific slugs to the real `/privacy` route at render time, plus locale-prefixes every other relative link — same spirit as `Footer.tsx`'s `getLocalizedUrl()`. If a real page at one of those slugs ever gets built, delete the matching entry from `LEGACY_INTERNAL_LINK_MAP`.
- Sitemap entry (`/cookies-policy`, `lib/routes.ts`) and `CookieBanner.tsx`'s banner text (links to both `/privacy` and `/cookies-policy`) already point here — see "Cookie banner" below.

### Header navigation (Strapi-driven, no route table in code)
- The header's nav links come entirely from the `header` single type's `navLinks` component (`title` + `targetId` only — no `href`, no route/anchor flag). `Header.tsx` and `MobileMenu.tsx` render every item generically through the shared `NavLink.tsx`; there is no per-item branching by title/position in either component.
- `NavLink.tsx` decides route vs. same-page anchor purely from the `targetId` value: if it starts with `/` (e.g. `/services`), it renders a real `next/link` navigation; otherwise it's treated as an anchor id, scrolled to via `scrollIntoView` + `pushState` **if that id exists on the current page** — see the cross-page anchor fix below for what happens when it doesn't. To point a nav item at a real page, change its `targetId` in the Strapi admin to a `/`-prefixed path — don't hardcode a title-string match in `Header.tsx`, that breaks on rename/locale and was deliberately avoided.
- **Cross-page anchor clicks used to be a silent dead click on any page without the target id.** `handleScroll` used to call `e.preventDefault()` unconditionally, then look up `document.getElementById(cleanTargetId)` **on the current page only**; if not found (e.g. clicking "Контакти", `targetId="contacts"`, from `/services`, `/privacy`, or `/cookies-policy` — none of which render a `<Contacts>` block), the function just returned and did nothing — no scroll, no navigation, no console error, despite the `<Link>`'s own `href` correctly pointing at `/${locale}#${cleanTargetId}` (which would have worked fine, since home/`/about`/every service-detail page do have that id). Fixed: `e.preventDefault()` now only fires inside the `if (element)` branch — when the id isn't on the current page, the click falls through to the `Link`'s normal navigation instead of being swallowed. `Contacts.tsx` (see "Contact form" below) has a companion `useEffect` that checks `window.location.hash === '#contacts'` on mount and scrolls to itself, since Next.js App Router's client-side transitions don't reliably auto-scroll to a hash the way a full page load does. This bug affected all three same-component instances at once: the desktop header nav item, its duplicate inside `MobileMenu`'s nav list, and `MobileMenu`'s own bottom `sidebarBtn` ("Консультація" CTA, also `targetId="contacts"`) — none of it was route-specific, it was the shared `NavLink` logic itself.
- **`activeClass` (passed by both `Header.tsx` and `MobileMenu.tsx` as `activeClass={styles.active}`) is only actually applied on the route branch** — `NavLink.tsx` reads `usePathname()` and appends `activeClass` when the current pathname matches the target route (or is a subpath of it, e.g. `targetId="/services"` stays active on `/services/licensing` too). It used to be accepted as a prop and silently never used at all (dead CSS — `.link.active`'s `font-weight` could never actually apply to anything); fixed, but the anchor branch (hash-based scroll targets) still doesn't compute an active state — that would need scroll-spy/`IntersectionObserver`, a separate, bigger task, not attempted here.
- **The root path (`href === /${locale}`) needs an exact-match exception, not prefix matching.** Strapi's "Головна" nav item used to have `targetId: "/home"` (a real gap, since the far more common `/uk` root URL never matched it); once that was changed to `targetId: "/"` in the admin, the *existing* `isActive = pathname === href || pathname.startsWith(\`${href}/\`)` check broke in a new way — `${href}/` for the root is just `/uk/`, which is a prefix of **every single page on the site**, so "Головна" ended up highlighted simultaneously with whatever other nav item was genuinely active (e.g. "Головна" + "Послуги" both underlined on `/uk/services`). Fixed by special-casing the root: `pathname === href` only, no `startsWith`, for `href === /${locale}` specifically — every other nav item keeps the prefix-match behavior (still correct and wanted, e.g. `/services` should stay active on `/services/licensing`). This is decided structurally (is this href literally the locale root?), not by hardcoding the "Головна" title — same anti-pattern avoided as elsewhere in this file.
- The same convention is reused in `Head.tsx`'s hero buttons (`primaryButton`/`secondaryButton`, from `headSection`, also just `title` + `targetId`): a local `buildHref(locale, targetId)` helper applies the identical `/`-prefixed-route-vs-anchor logic. `Button.tsx` itself is a plain `next/link` wrapper with no scroll-intercept behavior (unlike `NavLink`), so the href just needs to resolve to the right target.
- `Footer.tsx`'s "legal info" column (`legalTitle` + `legalLinks`, incl. the Privacy Policy link) renders for **both** locales now — it used to be `locale === 'en'`-only. **The `uk` locale's `footer` entry in Strapi has no real content for these fields yet** (`legalTitle` is a stray single-space string, `legalLinks` is empty) — the column now renders unconditionally in code, but showing an actual link on `/uk` requires filling in `legalTitle`/`legalLinks` for the `uk` locale in the Strapi admin; that's a content task, not a code task.
- **`MobileMenu`'s visual design was overhauled** (previously: flat solid `--obsidian` background, no dividers between nav items, `LangSwitch`'s "UA / EN" reading as two unrelated words with uneven spacing, a dull `--color-graphite` CTA button indistinguishable from the rest of the list, and a bare `×` close "button" with no real tap target). Now: `.sidebar` uses a subtle `linear-gradient(180deg, var(--obsidian) 0%, var(--ink) 100%)` for depth (still within the existing dark palette, no new color); nav `<li>`s get `border-top`/`border-bottom: 1px solid var(--line-dark)` dividers (the same "divider list" pattern already used on `/about`'s expertise list and `/services/[slug]`'s `mainContent` blocks) plus a `color-mix(in srgb, var(--paper) 8%, transparent)` hover/active tile background so each item reads as its own tappable zone, not a bare line of text; the CTA (`.sidebarBtn`) initially used `var(--focus)` (gold) as a solid background with `var(--obsidian)` text (matching `QuickContactButton.module.scss`'s `.fab`), then switched to `var(--steel-dim)` background + `var(--platinum)` text (6.33:1, WCAG AA) after the client asked for a more restrained gray instead of gold — `--steel-dim` reads as "one shade lighter than the sidebar's own `--obsidian`/`--ink` gradient," clearly clickable without competing for attention the way gold did — at `border-radius: 6px`, matching `Button.module.scss`'s base `.btn` (not a new radius value); `.closeBtn` is now an explicit 44×44px circular tap target (WCAG 2.5.5) instead of a bare oversized `×` character with no defined hit area. All three sections (nav / lang switch / CTA) are wrapped in one `.menuBody` div with `margin: auto 0` to center as a single group in the sidebar's remaining vertical space (`.closeBtn` sits outside `.menuBody` so it stays pinned top-right regardless of body height), and `.mobileLangGroup`/`.ctaGroup` both carry the same `margin-top: 24px` so the three sections read as consistent, evenly-spaced groups rather than scattered rows.
- **The UA/EN pill switch required extending `Header.module.scss` itself, not just `MobileMenu.module.scss`** — `LangSwitch.tsx` is one shared component (`Header.tsx` desktop + `MobileMenu.tsx`), so a visual change to how the *active* language is highlighted or how the divider renders has to happen in the CSS module that actually owns `.langSwitch`/`.activeLang`/`.divider` (`Header.module.scss`), since CSS Modules scope class selectors per-file — `MobileMenu.module.scss` cannot target another module's hashed class names by writing the same selector name again (that just creates an unrelated, never-applied class in its own module). The fix reuses the exact pattern already established for `--lang-inactive-color`: every new visual hook is a CSS custom property read with a safe fallback that reproduces the current desktop look exactly — `--lang-pill-gap`/`--lang-pill-bg`/`--lang-pill-border`/`--lang-pill-radius`/`--lang-pill-outer-padding`/`--lang-pill-padding` on `.langSwitch`/its `a`s (fall back to `4px`/`transparent`/`none`/`0`), `--lang-active-bg`/`--lang-active-color`/`--lang-active-radius` on `.activeLang` (fall back to `transparent`/`inherit`/`0` — `inherit` is the pre-existing "supertrick" that made the active language dark-on-light-header and light-on-dark-sidebar automatically), and `--lang-divider-display` on `.divider` (falls back to `inline`, i.e. an unset `<span>`'s natural default). `MobileMenu.module.scss`'s `.mobileLang` sets all of these to build the pill (touching-adjacent UA/EN, active language on a `var(--platinum)` chip with `var(--obsidian)` text, divider hidden) — confirmed via `getComputedStyle()` in a live Playwright check that desktop's `.langSwitch`/`.activeLang` compute to the exact same transparent/`0`/`4px` values as before the change, i.e. zero visual diff on desktop. If you ever need another per-context override of this shared component, extend this same custom-property list rather than duplicating `LangSwitch.tsx`.
- **The desktop `.desktopLang` wrapper now sets the same pill custom-property list as `.mobileLang`, just with compact desktop-appropriate values** — this is the reuse mechanism the pill design was built for in the first place: no new CSS class, no `LangSwitch.tsx` fork, just different values for the same hooks (`--lang-pill-padding: 4px 12px` vs mobile's `8px 20px`, `--lang-pill-bg: var(--mist)` + `--lang-active-bg: var(--paper)` instead of mobile's translucent-white-on-dark pair — reusing the exact `--mist`-backdrop/`--paper`-surface relationship already established for the contact form's inputs, not a new color pairing). Verified via computed-contrast check on a live render: active chip ~18:1, inactive text ~5.7:1 against the pill's own `--mist` background, both comfortably above WCAG AA on both locales.
- **A reported "mobile lang switch causes a full reload back to the homepage" did NOT reproduce as a hard reload/wrong-destination bug** (dev server + a full `next build && next start` production server, `page.on('request')` filtered to `resourceType() === 'document'`, and direct `href` inspection all confirmed exactly one client-side transition to `/en/services`, zero document requests, correct destination) — but a closely related, real issue was found: **the sidebar visually closed anyway**, even though nothing in the code calls `setOpen(false)` for a lang-switch click. Root cause, confirmed empirically (a manually-set `data-probe` attribute on the `.sidebar` DOM node, added via raw `element.dataset`, disappears after the locale-changing navigation): **`[locale]` is the outermost dynamic segment of the entire app** (`Header`/`MobileMenu` mount inside `app/[locale]/layout.tsx`, and there is no `app/layout.tsx` above it), so a navigation that changes the segment's *value* (`uk` → `en`) — unlike navigating between two pages under a *fixed* locale — causes Next.js to tear down and recreate that whole subtree rather than preserving it the way App Router layouts normally do across sibling-page navigation. `MobileMenu`'s `useState` for `open` genuinely remounts back to its initial `false`, which just looks like the menu "closed itself." Fixed by moving the persisted flag to a plain module-level variable (`wasOpenAcrossLocaleSwitch`, deliberately *not* `useState`/`sessionStorage`) — a JS module's scope isn't torn down by a client-side navigation the way a React subtree is, so it survives exactly this remount, while still correctly resetting on a real full page reload (new module evaluation) rather than leaking across browser sessions the way `sessionStorage` would. `openMenu`/`closeMenu` write to it alongside `setOpen`. `handleMobileClick` (nav items + the CTA) still calls `closeMenu()` exactly as before — only the lang-switch links were ever missing that call, and that omission is intentional now, not accidental. If you ever see similar "state reset for no apparent reason" symptoms elsewhere in `MobileMenu`/`Header`, suspect this same locale-segment-remount mechanism before assuming a logic bug in the component itself.
- **That fix alone still visibly "flickered"**: fixing `open` to restore `true` doesn't stop `.sidebar`'s own `transition: transform 0.3s ease` from firing — a `useEffect`-based restore (`useState(false)` then `setOpen(true)` in an effect after mount) still paints the freshly-remounted node in its *closed* position first, then animates it open a tick later, which is exactly the "slides in again" symptom, playing out on every locale switch even though the menu was never meant to visibly move at all. Fixed by reading `wasOpenAcrossLocaleSwitch` via `useState`'s **lazy initializer** (`useState(() => wasOpenAcrossLocaleSwitch)`) instead of a post-mount effect — the very first render of the remounted node already has `.active` applied, so there is no "before" paint on that DOM node for the transition to interpolate from, and no `useEffect` is needed at all for this anymore (removed). A genuine hamburger-click open still starts from a real `false` (the flag is only ever `true` after the user has actually opened the menu) and animates normally — verified live by sampling `getComputedStyle(...).transform` every frame for 600ms: a real open/close produces ~20 distinct interpolated matrix values, a locale switch produces the exact same matrix value on every single sampled frame (fully static, confirmed both by computed-style sampling and by screenshots taken at 30ms/150ms/550ms after the click — the menu never moves, only the text and the active pill relabel).
- **The structurally cleaner fix — rendering `Header`/`MobileMenu` above the `[locale]` segment entirely, so a locale switch never remounts them in the first place — was considered and deliberately deferred, not attempted.** It would need a real `app/layout.tsx` above `app/[locale]/`, which today doesn't exist (`<html lang={locale}>` currently lives in `app/[locale]/layout.tsx` itself, since that's the de facto root layout for this whole route tree); moving `Header` up would mean pulling `<html>`/`<body>` out to a new outer root layout, and rethinking how `Header`/`MobileMenu` still receive `locale` (they'd need it from something other than route `params`, e.g. parsing `usePathname()` client-side, since a component above the `[locale]` segment has no `params.locale` to read). That's a real architectural change with its own risk surface (CSP nonce plumbing, JSON-LD, cookie banner — all currently threaded through `app/[locale]/layout.tsx`, documented elsewhere in this file — would need re-auditing), not a quick win, so the module-variable + lazy-init workaround above is the current fix. Worth revisiting if more remount-related symptoms surface in this component.

### Accessibility (WCAG contrast, focus/inert)
- **`--steel` (`#8E8E93`) fails WCAG AA 4.5:1 against light backgrounds** (`--platinum`/`--paper`/`--mist`) — only ~3.1:1. `--steel-dim` (`#5f5f66`, ~6:1+ against any of those) is the replacement everywhere text needs to be visibly secondary/muted on a light surface: `Contacts.module.scss`'s `.formSubtitle` and the resting (non-focused) state of `.fieldLabel` (floating labels), and `ArticleNav.module.scss`'s `.asideTitle` ("На цій сторінці"). Don't reach for `--steel` for body/label text on a light background — it reads fine visually but fails contrast tooling every time.
- **`LangSwitch`'s inactive-language color can't be a single static token** — the same component (`Header.module.scss`'s `.langSwitch`/`.activeLang` classes, reused via `LangSwitch.tsx` in both `Header.tsx` and `MobileMenu.tsx`) renders on a light background (desktop Header, `--platinum`) *and* a dark one (mobile `.sidebar`, `--color-obsidian`) — no single gray passes 4.5:1 on both (`--steel`: 3.1:1 light / 6.25:1 dark; `--steel-dim`: 6:1+ light / 3.2:1 dark). Fixed via a CSS custom property with a per-context override: `.langSwitch a:not(.activeLang) { color: var(--lang-inactive-color, var(--steel-dim)); }` in `Header.module.scss` (fallback = light-context value), and `MobileMenu.module.scss`'s `.mobileLang { --lang-inactive-color: var(--steel); }` overrides it for the dark context. The `:not(.activeLang)` isn't about excluding the active state stylistically — it's a deliberate specificity bump (two classes instead of one) needed to reliably beat `MobileMenu.module.scss`'s unrelated `.sidebar a { color: ... }` rule, which has equal specificity and was silently winning by bundle order before this fix.
- **`MobileMenu.tsx`'s closed `.sidebar` has `inert={!open}` alongside `aria-hidden={!open}`** — the same fix already applied to `ContactModal.tsx` for the same underlying problem (`aria-hidden` on a container whose descendants are still focusable is an axe/Lighthouse `aria-hidden-focus` violation; `inert` removes them from both the focus order and the accessibility tree in one attribute, no per-link `tabIndex` management needed). This is a real, functional fix, not just a lint silencer — before it, `Tab` could genuinely focus into the closed mobile menu's links.
- If you add a full accessibility audit again, use `@axe-core/playwright` against a running `next build && next start` (not `next dev` — font/script optimizations differ) — it caught all of the above plus `color-contrast` and `aria-hidden-focus` with exact element targets and computed colors, far more reliable than eyeballing.

### Cookie banner (`CookieBanner`/`CookieSettingsLink`) — GDPR/ePrivacy
- `app/[locale]/components/cookies/CookieBanner.tsx`, rendered globally in `layout.tsx`, is the **only** place in the app allowed to load Google Analytics. It used to be loaded unconditionally by a `<GoogleAnalytics>` call in `layout.tsx` regardless of consent — that was a real ePrivacy violation and was removed; don't reintroduce a second GA-loading path anywhere else, ever.
- State is `consent: "pending" | "granted" | "denied"` plus a separate `showBanner: boolean` — these are deliberately not the same thing. `showBanner` controls whether the banner UI is currently on screen; `consent` controls whether the GA `<Script>` tags render. This split is what lets the banner be **reopened** later (via `CookieSettingsLink`) without re-triggering GA or losing the stored choice.
- Consent is persisted in `localStorage` (`harlib_cookie_consent`) as `{ choice, timestamp, policyVersion }` — not a bare string. Bump the module-level `POLICY_VERSION` constant whenever what the site tracks changes materially (that's the only way a stored old consent becomes visibly "stale" for a human auditing it — there's no automatic re-prompt on version bump, that's a deliberate scope decision, not an oversight). A separate stable, non-identifying `consentId` (`crypto.randomUUID()`, its own `localStorage` key `harlib_consent_id`) is generated once and reused across choice changes — it exists purely to correlate this browser's local record with its server-side log entry (see root `CLAUDE.md`'s "Cookie consent" section for the `/api/consent` → Strapi `consent-log` write path), not to identify a person.
- The Accept/Reject buttons are deliberately styled with **equal visual weight** (`CookieBanner.module.scss` — same padding/font-weight/border thickness, only fill-vs-outline differs) — don't make one a subdued/ghost button and the other a solid CTA, that's a known EDPB-flagged dark pattern ("unequal prominence") and was fixed once already.
- The privacy-policy link inside the banner text (`/${locale}/privacy`) renders for **both** locales — it used to be `en`-only and pointed at a non-existent `/privacy-policy` route (404) before both were fixed. If you touch this text again, keep the link present for `uk` too. The banner text now links to **two** separate pages — `/privacy` and `/cookies-policy` (see below) — don't collapse them back into one link, they're legally distinct documents.
- Two custom `window` events tie this component to the rest of the app — grep for the constant name, don't hardcode the string elsewhere:
  - `COOKIE_SETTINGS_EVENT` — `CookieBanner` **listens**; `CookieSettingsLink.tsx` (rendered in `Footer.tsx`, both locales) dispatches it to reopen the banner later ("Налаштування cookies"/"Cookie Settings") without touching the already-stored choice.
  - `COOKIE_BANNER_VISIBILITY_EVENT` — `CookieBanner` **dispatches** it whenever `showBanner` changes; `QuickContactButton.tsx` listens so it can hide itself and pause its own bubble timer while the cookie banner is on screen (see "Contact modal" below) — the two bottom-of-screen popups must never show at once.

#### Divergent slugs / LangSwitch / hreflang
- Because `service-page` slugs can now differ per locale, naive "swap the locale segment in the pathname" is wrong for `/services/[slug]` — but that's still exactly what `LangSwitch.tsx` does for every *other* page type (correct and unchanged there).
- `LangSwitch`/`Header`/`MobileMenu` render in `app/[locale]/layout.tsx`, a **sibling** of the routed page content, not a parent — so a page's own server-fetched data (documentId, alternate-locale slug) can't be passed down as props. Fixed via a small internal proxy route, `app/api/service-page-locale-slug/route.ts` (`GET ?slug=&fromLocale=&toLocale=`): resolves `documentId` via `fetchStrapiBySlug`, then the alternate slug via `fetchServicePageSlugInLocale(documentId, toLocale)`. `LangSwitch.tsx` calls this client-side (`fetch`, same-origin, no CSP changes needed) only when `usePathname()` matches `/^\/[a-z]{2}\/services\/([^/]+)$/`.
- Until the client-side fetch resolves (or if there's genuinely no counterpart, e.g. `crypto`), `LangSwitch` falls back to the locale's `/services` catalog — **never** the old unsafe "reuse the same slug" behavior, and never a 404. This is a real (small) hydration gap: the raw SSR HTML's initial `href` can briefly be the catalog link until the client fetch resolves. Accepted because (a) real users have JS by the time they click, (b) the authoritative SEO signal is the server-rendered `<link rel="alternate" hreflang>` in `<head>`, fixed properly server-side (next point), not this in-body nav link.
- Server-side, `getAlternates()` (`lib/metadata.ts`) takes an optional third param `localizedPaths?: Partial<Record<Locale, string | null>>` — `null` for a locale means "deliberately doesn't exist here, omit from hreflang" (the `crypto` case: no `uk` line at all, `x-default` falls back to the current locale's own path since the default locale `uk` has no version). `app/[locale]/services/[slug]/page.tsx`'s `generateMetadata()` builds this via `getLocalizedPaths(documentId, currentLocale)`, which calls `fetchServicePageSlugInLocale` for every other locale.
- Test cases confirmed live: `uk/services/kapitalizaciya` → EN link resolves to `/en/services/capital` (not the homepage, not 404); `en/services/crypto` → UA link resolves straight to `/uk/services` (catalog), and its hreflang alternates list only `en` + `x-default`, no `uk` line.
- **On Windows/Git Bash, never pass Cyrillic text inline as a `curl -d '...'` argument** — it silently mangles the encoding (Strapi receives mojibake) even though the shell's own UTF-8 handling is fine; the corruption happens in argument passing to curl specifically. Write the JSON payload to a file first (verify the bytes with `xxd` if in doubt) and send it with `curl --data-binary @file`.
- **Locally, `.next/cache/fetch-cache` persists Strapi responses across `npm run build`/`npm start` cycles within the same session**, independent of the 60s `revalidate` window — after publishing new Strapi content, a freshly rebuilt/restarted local server can still serve a stale list (this bit the `service-pages` listing page specifically after a batch of new entries was published). If freshly-published content isn't showing up locally, delete `.next/cache/fetch-cache` and rebuild before assuming a code bug.

### Design tokens
- `app/[locale]/globals.css` defines two overlapping token sets: the canonical one (`--obsidian`, `--ink`, `--platinum`, `--paper`, `--steel`, `--steel-dim`, `--line-light`, `--line-dark`, `--focus`, `--mist`) and legacy `--color-*` duplicates (`--color-obsidian`, `--color-platinum`, etc.) with identical values. **Use the canonical (non-`--color-*`) names in new/edited code** — the `--color-*` set is being phased out wherever touched, not removed outright (still referenced in a few untouched places like `Head.module.scss`'s buttons). `--focus` (`#c9a227`, gold) is the accent color for `ArticleNav`'s active indicator on service pages — **the contact form deliberately does not use it** (see "Contact form" below), don't "fix" that back to gold thinking it's an inconsistency. `--mist` (`#F2F2F2`) is a light neutral gray one step darker than `--platinum` — added specifically so a white surface (e.g. form inputs) can sit visibly on top of a gray one; reach for it before hardcoding a new gray or reusing `--platinum` as a "backdrop" (it's already the page's own background, so there'd be no contrast).
- No `font-family` custom properties exist — fonts are loaded via `next/font/google` in `layout.tsx` (`Inter` weights **400/500/600**, `Playfair_Display` weights **400/600**) and applied as global classNames on `<body>`; a component picks a family by hardcoding the string `'Inter', sans-serif` / `'Playfair Display', serif` in its own SCSS module. H1/H2 pattern: Playfair Display, weight 600, uppercase, 64px desktop stepping down to 28px mobile (see `Head.module.scss` `.title` or `Title.module.scss` `.h1`/`.h2` — both now defined; `Title.tsx` supports an `"h1"` case and the SCSS backs it, though `Head.tsx` still uses its own local `<h1>` instead of `<Title>`, matching precedent).
- **Every `font-weight` value used anywhere in the codebase must be one of the weights actually declared in `layout.tsx`'s `Inter({weight:...})`/`Playfair_Display({weight:...})` calls** — the browser silently substitutes the nearest loaded weight for anything else (no error, no visual crash), which is exactly how this drifted out of sync before: `About.module.scss`/`Block.module.scss` had `font-weight: 500` and `Partner.module.scss` had `800` for Playfair (only 400/600/700 were loaded at the time), and `services/page.module.scss`'s `.cardDesc` + `services/[slug]/page.module.scss`'s `.intro` had `font-weight: 300` for Inter — all fixed to the nearest real loaded weight (`600`/`400`) rather than adding more weights just to match one-off CSS values. `Inter`'s `300` and `Playfair_Display`'s `700` were dropped entirely from `layout.tsx` after confirming (via `grep` across every `.scss`, not assumption) they had no real remaining usage — **`grep` the whole `app/` tree for the exact weight before either adding it to `layout.tsx` or assuming a usage is safe to drop**; a narrower/windowed search missed two real, frequently-rendered usages of `font-weight: 300` once during this same audit.
- **`layout.tsx`'s `getFontPreloadHrefs()` manually emits `<link rel="preload" as="font" type="font/woff2">` for the Inter/Playfair woff2 files, because `next/font`'s documented automatic preload ("preloaded on all routes wrapped by the layout it's called in") was empirically confirmed absent** — checked the raw served HTML (both `npm run dev` and a full `next build && next start`) and found zero `<link rel="preload" as="font">` tags at all, despite `inter`/`playfair` being declared in this exact layout. The likely cause: every route here is fully dynamic (`ƒ`) because of the `headers()` call this file already makes for the CSP nonce (see "Config/security" below) — Next's automatic font-preload injection appears not to carry over reliably for fully dynamic SSR routes the way it does for statically-analyzable ones, though this isn't officially documented as a limitation. A PageSpeed/Lighthouse audit on `/uk` flagged exactly this: the two woff2 files only got discovered after the browser parsed the separate `@font-face` CSS chunk (`HTML → CSS → font`, ~922ms of critical-chain delay), instead of being fetched in parallel with the CSS.
  - **The fix reads `next-font-manifest.json`** (`.next/server/next-font-manifest.json` in production, `.next/dev/server/next-font-manifest.json` in dev) — an internal Next.js build artifact, not a public API, but it's the exact file Next itself generates (and would use for this same feature) listing precisely which woff2 files each route's font declarations resolve to. Confirmed by inspecting it directly: **every route lists the identical 2 files** (`Inter`/`Playfair_Display` are applied uniformly at `<body>` level in this one shared layout, so there's no per-route variation), which is why reading it once in this shared layout and preloading unconditionally is correct — no per-route branching needed.
  - **Hardcoding the resulting hashed filenames was deliberately avoided** — `next/font` regenerates content hashes on every build, so a hardcoded `href` would silently go stale (still 200, but no longer the actually-used file) on the very next deploy. Reading the manifest at runtime keeps this permanently in sync with whatever the current build actually produced.
  - Wrapped in `try/catch` with an empty-array fallback per candidate path — if Next.js ever changes this internal manifest's location or shape in a future version, the site loses only this optimization, not the ability to render.
  - **Needs `/*turbopackIgnore: true*/` comments on both the `fs.readFileSync` call and (redundantly, doesn't hurt) the `path.join` calls** — without it, Turbopack's build-time file tracer (NFT, used for its own dependency analysis) flags this as a "dynamic requires — the whole project was traced unintentionally" warning, because it can't statically prove the `fs.readFileSync(manifestPath, ...)` argument resolves to a fixed, safe file. Confirmed via `git stash` that the warning is new (introduced by this exact code, not pre-existing) and that only the `fs.readFileSync` ignore comment — not just the `path.join` ones — actually silences it. Harmless in practice either way (this project deploys via `pm2` with the full repo present, not `output: 'standalone'`'s trimmed serverless bundle, so the NFT list itself is unused here), but worth keeping clean.
  - Verified live via Resource Timing API (`performance.getEntriesByType('resource')`): the two preloaded files show `initiatorType: "link"` and start ~50ms earlier than the other (non-preloaded, still CSS-discovered) font subset files, which show `initiatorType: "css"` — direct confirmation the preload is doing its job, not just present in the HTML inertly.
  - `font-display: swap` was already the default (`next/font`'s own default value, unchanged) and confirmed present in the generated `@font-face` CSS — no change was needed there. Inlining the `@font-face` declaration itself (rather than leaving it in next/font's separate CSS chunk) was considered and not pursued: the explicit preload already achieves the same practical outcome (the browser fetches the font in parallel with CSS discovery instead of waiting on it), and next/font doesn't expose a supported way to force its generated CSS to be inlined instead of chunked.

- `app/[locale]/layout.tsx` only holds metadata shared by *every* page: `metadataBase`, `title.template` (adds the `| HARLIB` suffix automatically), `verification`, `icons`. Don't add page-specific title/description/OG there — it won't be page-specific once you do. (This used to be violated — a full hand-rolled `Metadata` object, including home's own title/description, lived here instead of in `app/[locale]/page.tsx`'s own `generateMetadata()`. For a **DB-driven page family** (many entries from one collection type, like `service-page`), `STATIC_ROUTES` doesn't apply — see "Service pages" above for the pattern (`sitemap.ts` queries the collection type directly instead).

Rendered via the shared `app/[locale]/services/Breadcrumbs.tsx` component (used by both pages) alongside a matching **visual** breadcrumb trail above the page's `<h1>` — same small/muted typography pattern as `ArticleNav`'s `.asideTitle` but without `text-transform: uppercase` (a long service name in all-caps read as too heavy).

  - `buildWebPageJsonLd({ name, description, url })` — on `/privacy` and `/cookies-policy` (both indexed normally, `noIndex` is not set on either — legal documents are still part of the site's trust signals for Google).

### Contact form
- `app/[locale]/home/section/contacts/Contacts.tsx` is a client component, rendered on both `home/page.tsx` and every `app/[locale]/services/[slug]/page.tsx` — each caller fetches its own `contact` single-type data via `fetchContactData(locale)` and passes it as `data`; the component itself has no fetch logic. It POSTs form data as JSON to `app/api/contact/route.ts`.
- The form includes a required consent checkbox (`name="consent"`, linking to `/${locale}/privacy`) and a hidden honeypot field (`name="website"`, visually off-screen via `.honeypot`, `aria-hidden`, `tabIndex={-1}` — not `display:none`, since some bots skip those but still auto-fill any DOM-present text input).
- `route.ts` sends mail via `nodemailer` using `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` / `SMTP_USER` / `SMTP_PASS` env vars, always to `info@harlib.com.ua`, with `replyTo` set to the submitter's email. It validates `name`/`email`/`phone`/`consent` server-side (client `required` alone doesn't stop a direct POST), escapes every user-supplied field (`escapeHtml`) before interpolating into the email's HTML body — don't remove that when touching this file, it's the only thing preventing HTML injection into the notification email — and silently returns `{success:true}` without sending mail if the honeypot field is non-empty.
- **Field length caps and phone format are enforced on both client and server, in lockstep.** `Contacts.tsx` sets `maxLength` on all 5 fields (name 100, company 150, email 254 — the RFC 5321 max, phone 20, message 2000); `route.ts`'s `MAX_LEN` constant mirrors the same numbers and rejects (`400`) anything over them, since `maxLength` is a client-only affordance a direct API `POST` skips entirely. If you ever change one of these limits, change both — they're two independent literals, not derived from a shared constant (kept simple since there's no shared client/server module for this today).
- **Phone format validation deliberately does NOT use the HTML5 `pattern` attribute** — a QA audit found that native browser validation messages (`required`/`type="email"`'s built-in popups) are tied to the *browser's* UI language, not the page's `lang` attribute (a Chromium limitation; confirmed both `uk`/`en` pages showed English-only native tooltips), so a native `pattern` mismatch would've shown the same unlocalizable popup. Instead, `PHONE_RE` (`/^\+?[0-9\s\-()]{7,20}$/` — accepts `+380...`/international numbers with spaces, dashes, parens, deliberately loose rather than over-strict) is checked in `handleSubmit` *before* the `fetch` call, and on failure sets `errorMessage` to a `locale`-branched string, shown via the error banner described below — this is the one place in the component that gives a real localized message instead of relying on native browser validation. The identical `PHONE_RE` is re-checked in `route.ts` since the client check is trivially bypassed with a direct `POST`.
- Submission status (`idle | sending | success | error`) is *not* reset to `idle` after send — a past bug did this in a `finally` block, which meant the success/error UI was visible for a single render tick. The message text comes from an `errorMessage` state (set right before `setStatus('error')`, either to the phone-format string above or the generic submit-failure string) rather than being hardcoded inline in the JSX — needed once there were two different possible error reasons to show through the same banner.
- **Success and error states are deliberately hard to miss — a past version only showed a thin `aria-live` text line under the button, which a QA pass found users could submit past without noticing anything happened.** First fix replaced the whole form with a success screen (checkmark + "send another" button); that was then explicitly reverted — the form must always stay visible and ready for a new message, so success is now confirmed by a separate `Toast` component (`app/[locale]/components/toast/Toast.tsx`) instead of anything replacing the form. On success, `handleSubmit` calls `formRef.current?.reset()` (fields must now be cleared manually, since the form no longer unmounts/remounts the way the old success-screen version did) and sets a `toastMessage` string that mounts `<Toast>`. `Toast` auto-dismisses after `durationMs` (default 4500ms), supports an earlier manual "×" close, and fades in/out via a `.closing` class swap timed to match its own CSS animation duration (`EXIT_ANIMATION_MS`, 250ms) so `onClose` (which unmounts it) fires only after the fade-out finishes, not before. `role="status"` + `aria-live="polite"` is the same accessibility mechanism the old inline text line used. Error state is unchanged by this: on `status === 'error'` the form stays visible and usable, showing the colored `.errorBanner` (icon + text, `var(--error)`) above the submit button — errors were never replacing the form, only success was, so only success needed to change.
- **`Toast` renders via `createPortal(..., document.body)`, same as `ContactModal.tsx` — this isn't optional here.** `Contacts` is wrapped in `<Reveal>` (`home/page.tsx`), whose `.reveal` class sets `will-change: opacity, transform` permanently (not just mid-animation) — per the CSS spec, `will-change: transform` on an ancestor creates a new containing block for `position: fixed` descendants, same as an actual `transform` would. A first version of `Toast` rendered inline inside `Contacts` and was fixed-positioned relative to that `.reveal` div instead of the real viewport — confirmed via `getBoundingClientRect()` showing the toast ~140px *above* the visible viewport (off-screen) after scrolling to the contacts section, not pinned to the top like it should. Portaling to `document.body` sidesteps any ancestor's `transform`/`will-change` entirely, regardless of where `<Contacts>` is mounted on a page. If you ever add another `position: fixed` UI element as a descendant of a `<Reveal>`-wrapped section, it needs the same portal treatment — this isn't specific to `Toast`.
- **`--success` (`#15803d`) and `--error` (`#b91c1c`) in `globals.css` are the site's first semantic status colors** — every other color on the site is a neutral (`--obsidian`/`--steel-dim`/etc.); these two exist specifically because success/error states can't be visually distinguished from each other or from normal text using only grayscale tokens. Both were chosen for ≥4.5:1 WCAG AA contrast as text on `--paper`/`--mist` (~4.6:1 and ~4.8:1 respectively) — same contrast discipline as every other color decision in this file. The error banner's background/border use the established `color-mix(in srgb, <token> X%, ...)` pattern already used for the input focus glow, not a new hardcoded tint.
- `home-page.contactsSection` (the Strapi field/component, not the frontend section) is now **orphaned** — the `contact` single type replaced it as the data source, but the old field was deliberately left in the schema and its content untouched to avoid data loss. Don't resurrect a `fetchStrapi('home-page', {... contactsSection ...})` call; use `fetchContactData` instead. Removing the old field from the schema entirely is a pending cleanup decision, not yet done.
- **Field labels (`ІМ'Я`, `EMAIL`, etc.) are CSS-only floating labels, not a separate row above each input.** This only works because each `<label>` sits *after* its `<input>`/`<textarea>` in the JSX (associated via `htmlFor`/`id`, not the old wrapping-label pattern) and every field has `placeholder=" "` (a literal space) — `:placeholder-shown` never matches without a `placeholder` attribute present at all, and the sibling-combinator CSS (`.input ~ .fieldLabel`, `.input:not(:placeholder-shown) ~ .fieldLabel`) requires that DOM order. If you ever revert to wrapping `<label>text<input/></label>`, the floating animation silently stops working (label just renders inline, no compile/runtime error). `.textarea ~ .fieldLabel` gets its own resting-position override (top-anchored, not vertically centered like `.input`'s) so the label doesn't float mid-box on the taller `message` field.
- The form card's visual language — `box-shadow`/`border-radius` on the card, `inset` shadow + `color-mix(in srgb, var(--steel-dim) 22%, transparent)` glow on input `:focus`, `translateY(-2px)` + shadow on the submit button's `:hover` — deliberately reuses only existing tokens (`--line-light`, `--steel-dim`) and mirrors the lift/shadow convention already used by `QuickContactButton`'s hover, not a one-off. The card itself is capped at `max-width: 500px` and centered in its grid column (`margin-inline: auto`) — it used to stretch to fill the whole column.
- **Two-tone surface, deliberate:** `.form`'s own background is `var(--mist)` (light gray), while `.input`/`.textarea` are `var(--paper)` (white) — the fields need to read as distinct raised surfaces against the card, not blend into it. Don't set them to the same value "for consistency"; that was the previous (flatter) look and is what this was changed away from.
- **This form's focus/hover accent is `var(--steel-dim)`, not `var(--focus)`** (deliberately, unlike `ArticleNav` on service pages, which does use the gold `--focus` accent for its active indicator — that's a separate, intentionally different context, not an inconsistency to "fix"). `--obsidian`/`--ink` were considered and rejected: both are visually almost identical to the text's own resting color (`--obsidian`), so a hover/focus state using either wouldn't read as a state change at all. `--steel-dim` (#5f5f66) gives ~6:1 contrast against `--paper`/`--platinum` (WCAG AA requires 4.5:1) while still looking clearly different from the resting text color.
- `formDisclaimer` (the text under the submit button) has **no CSS rule in `Contacts.module.scss`** — `styles.formDisclaimer` resolves to `undefined`, so it renders with only inherited/default `<p>` styling. Pre-existing gap, not yet fixed.

### Config/security
- `next.config.ts` whitelists the Strapi host (`31.131.18.174:1331`) for images (`images.remotePatterns`) and sets HSTS/COOP/X-Frame-Options/X-Content-Type-Options headers. If the Strapi host/port ever changes, update `images.remotePatterns` here.
- **`app/[locale]/layout.tsx`'s `<head>` has `<link rel="preconnect" href={getStrapiURL()} />`** (`getStrapiURL()` from `lib/api.ts` — the same helper `fetchStrapi()` itself uses, reused here instead of hardcoding the host a third time) — speeds up the connection to Strapi for `next/image`-optimized uploads (founder photo, etc.). **Confirmed via the live production HTML/CSP** (not assumed) that this is still the real image origin: `curl https://harlib.com.ua/uk` shows `/_next/image?url=http%3A%2F%2F31.131.18.174%3A1331%2Fuploads%2F...`, and the live CSP's `img-src`/`connect-src` both list the same raw IP. `admin.harlib.com.ua` does resolve (same IP) but isn't used anywhere in the deployed frontend yet — before ever repointing `images.remotePatterns`/CSP/this `preconnect` at that domain instead of the IP, re-verify with the same live-HTML/CSP check, don't assume a DNS entry existing means the app has been migrated to it.
- **`Content-Security-Policy` is NOT in `next.config.ts` anymore — it's generated per-request in `proxy.ts`, nonce-based.** This used to be a single static string in `next.config.ts`'s `headers()`, with `script-src 'unsafe-inline'`; that's fundamentally incompatible with a per-request nonce (a static header can't carry a fresh value each time), so the whole CSP was moved. `proxy.ts` generates a `crypto.randomUUID()`-based nonce on every request, wraps the existing `next-intl` `createMiddleware` call (mutates `request.headers` with `x-nonce`/CSP *before* delegating to it, then also sets `Content-Security-Policy` on the returned response), and the policy is `script-src 'self' 'nonce-{value}' 'strict-dynamic' https://www.googletagmanager.com` (no more `'unsafe-inline'`; `'unsafe-eval'` only in dev — React/Next don't need it in production). `style-src` still has `'unsafe-inline'` — untouched, out of scope (would additionally require nonce-ing every inline `style={{}}` usage, e.g. `privacy/page.tsx`'s hand-rolled inline styles).
- **`next.config.ts`'s `experimental.inlineCss: true` converts every Next-generated `<link rel="stylesheet">` into an inline `<style data-precedence>` tag, production builds only** — added after a PageSpeed/Lighthouse audit flagged "requests that block rendering" (~820ms) caused by the 4 CSS chunks this app's Turbopack build produces (`globals.css` + per-segment CSS Modules). Investigated the other options this kind of audit usually suggests, and all turned out to be dead ends for this specific stack, in order:
  - `experimental.optimizeCss` (critters/beasties-based critical-CSS extraction) — traced through `next/dist/server/post-process.js`: it's only ever `require`d from `server/render.js`, the **Pages Router** SSR renderer. `app-render/*` (App Router's actual rendering path) never references it. This project is 100% App Router (no `pages/` directory) — enabling this flag would do nothing but add an unused `critters` dependency.
  - Webpack's `splitChunks`/`optimization` config — inapplicable outright, since this project's build banner says `▲ Next.js 16.2.4 (Turbopack)`; Turbopack doesn't read webpack's `optimization` config, and its own `next.config.ts`-exposed `turbopack.*` options (`root`/`rules`/`resolveAlias`/`resolveExtensions`/`debugIds`) have no chunk-splitting-strategy knob at all.
  - `experimental.cssChunking` (the actual Turbopack-era equivalent lever) was already at its default, most-aggressive-merge setting (`true`) — the 4 chunks are already Next's best-effort consolidation of this app's real CSS import graph; `'strict'` only produces *more* chunks, and there's no more-merged-than-`true` option to reach for.
  - The "defer non-critical CSS via `rel=preload as=style onload` " trick doesn't apply here either — that technique only works on `<link>` tags you hand-author yourself; every stylesheet on this site is Next's own auto-injected CSS-Modules output, not a manually-linked stylesheet (confirmed via `grep` — no `<link rel="stylesheet">` written anywhere in this codebase's JSX).
  - Given all of the above, `inlineCss` was the one remaining, officially-documented, App-Router-native lever for exactly this problem (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/inlineCss.md`). Its own docs frame the ideal use case as atomic CSS (Tailwind) and warn inlining "large" bundles hurts repeat-visitor caching/TTFB — judged an acceptable trade here specifically because this site's total CSS is small (~11KB gzipped for a page, confirmed by measuring the same 4 chunks pre-fix) and it's a marketing/lead-gen site where first-time-visitor FCP/LCP matters more than repeat-session stylesheet caching. **Verified safe against this site's specific CSP** before enabling: `style-src` already carries `'unsafe-inline'` (see above), so the `<style>` tags this feature generates — which carry no nonce, since Next has no knowledge of this app's custom nonce mechanism — are not blocked. Confirmed live (production build only; the feature explicitly doesn't apply in `next dev`): `<link rel="stylesheet">` count drops to 0 and a single inline `<style data-precedence="next">` appears instead, across all 10 spot-checked routes/locales, zero console errors, and a screenshot taken at the earliest possible (`waitUntil: 'commit'`) paint shows fully-styled content with no FOUC — styles arrive attached to the HTML itself, so there's nothing to flash from.
- **Every inline `<script>` in the app needs its `nonce` threaded through explicitly** — Next.js does NOT automatically nonce a `next/script` `<Script>` or a `dangerouslySetInnerHTML` script tag just because the CSP header carries one; only Next's own framework/hydration scripts get it automatically. Two places currently need it: `app/[locale]/components/seo/JsonLd.tsx` (`nonce` prop → `<script nonce={nonce}>`, every page that renders `<JsonLd>` reads `x-nonce` itself via `headers()`) and `CookieBanner.tsx` (`nonce` prop, threaded from `layout.tsx` since `CookieBanner` is a Client Component and can't call `headers()` itself — applied to both the external `gtag/js` `<Script>` and the inline GA-init `<Script id="google-analytics">`). If you ever add another inline script or another `<Script>` anywhere, it needs the same treatment or it will be silently blocked by CSP with no `'unsafe-inline'` fallback.
- **`JsonLd.tsx`'s `<script>` has `suppressHydrationWarning`** — specifically because of the `nonce` attribute, not a blanket "silence hydration errors" move. Browsers deliberately hide a `<script>`'s real `nonce` value (both the attribute and the `.nonce` IDL property read back as `""`) the moment the element is inserted into the DOM, as a CSP hardening measure against JS reading nonces back out — so React's hydration diff always sees a mismatch (server sent the real nonce, the live DOM reads back empty) even though the nonce did its job correctly before hydration ever ran. Confirmed via the HTML spec's nonce-hiding behavior and `facebook/react#26028` (React itself has no special-case for this, hence the generic warning) — not a real bug, and an attribute-only mismatch means React keeps the server-rendered node as-is with no re-render/flash. `CookieBanner.tsx`'s two `<Script>` tags don't need the same treatment: both use `strategy="afterInteractive"`, which next/script injects client-side *after* hydration (confirmed: the GA script tag is absent from the raw server-rendered HTML entirely), so there's no server-vs-client DOM to diff against in the first place.
- **Nonce-based CSP requires every page to be dynamically rendered** (calling `headers()` forces this automatically — Next.js treats it as a Dynamic API) — static generation/ISR/PPR are incompatible with per-request nonces. This isn't a new constraint this project runs into in practice: every real content route was already `ƒ` (Dynamic) before this change (they all fetch Strapi on every request), so nothing needed converting. Only `/`, `/_not-found`, `/robots.txt`, `/sitemap.xml` remain static — none of them render `<JsonLd>`/`<CookieBanner>`, so this doesn't matter for them.
- **Trusted Types (`require-trusted-types-for 'script'`) is deliberately NOT enabled** — evaluated and rejected for now. `JsonLd.tsx`'s `dangerouslySetInnerHTML` (React's only way to set a `<script>` tag's content) has no native Trusted Types support in React, and `<script>` elements need a `TrustedScript` specifically (not just `TrustedHTML`) — enabling the directive without a compatibility policy would break JSON-LD rendering outright. Next.js 16.2.4 also has zero documented Trusted Types support, so there's open risk around its own internal RSC/hydration scripts too. If this is revisited, start with `Content-Security-Policy-Report-Only` first to see real violations before enforcing.
- Styling is SCSS Modules (`*.module.scss`) per-component, plus a global `app/[locale]/globals.css`.
- **Strapi API tokens have two independent permission surfaces** — the Public role (Settings → Users & Permissions → Roles → Public) and each API token's own scoped permissions (Settings → API Tokens → edit token → permissions). Granting a content-type's `find`/`update` on one does **not** grant it on the other; a token can 403 on a content-type the Public role can already read. When a token unexpectedly 403s on something that works unauthenticated, check the token's own permissions first, not the Public role.
- The Strapi backend (`server/`) is deployed remotely at `31.131.18.174:1331` — local `npm run dev` in `law-firm/` points at that remote instance by default via `NEXT_PUBLIC_STRAPI_URL` in `.env`, not a local Strapi. Content-type changes made in `server/src/api/` need the remote Strapi process restarted to register (filesystem-defined, loaded at boot) before they're queryable — that's a deploy action, not something a local `npm run dev` picks up on its own.
- **`law-firm/` is a git repo with a history of uncommitted work vanishing** — a "discard all changes" action in an editor's Source Control panel (or `git checkout .` / `git restore`) only reverts *tracked* files back to the last commit; it does not touch new/untracked files, which is why a mass revert can look partial (some files survive, others don't). If a lot of code suddenly "reverts itself" or a fix you made earlier in a session stops working, run `git status`/`git diff` first to check whether it's an actual revert before assuming a build/cache issue — and commit meaningful checkpoints rather than leaving substantial work uncommitted for long stretches.
